날짜: 2026-08-04 (§3.2 정정 2026-08-05) · 브랜치: `worktree-phase3-5-l2-rebaseline`

> **이 문서의 목적** (§9.1): "L1에서 통과했던 값이 L2에서 얼마나 달라지는가"를

**①이 가장 컸다**: 유령 노드가 살아 있으면 판정이 통째로 오염돼 **변경 전 코드의
v2 baseline 조차 재현되지 않았다**. 이 오염은 재기준화 도중 내가 내린 중간 결론
하나(§3.2 의 "RTF 캡이 게이트 성립 조건")까지 오염시켰고, 정리 목록을 완성한 뒤
재측정해 **정정했다** — 캡의 근거는 "없으면 게이트가 깨진다"가 아니라
"없으면 운영점이 부하에 좌우된다"이다.

**가장 중요한 방향성**: 정면·횡단·자전거 계열의 최소 이격이 v2 대비 **전부
개선**됐다 (head_on +0.315 m, crossing +0.183 m, social_box_diag +0.244 m).
L2 의 근거리 유입과 조밀한 근접장이 낮은 프레임률(5.55 Hz)의 손실을 상쇄하고도
남았다. 손실이 나타난 곳은 **타이밍 양자화에 민감한 양보 래치 하단 꼬리**
하나이며(§5.3), 이는 실기에서도 재현되리라 예측한다.

> ⚠ **미해결 2건은 둘 다 판정 기준·튜닝에 대한 결정을 요구하며, 재기준화가
> 임의로 바꿀 사안이 아니라 판단해 그대로 남겼다** (§5.2, §5.3).

## 2. 파라미터 재유도 델타

### 2.1 근거리 사각 의존 (🔴 유도 전제가 바뀐 항목)

v2의 유도식은 `min_range 0.8 − robot_half_length 0.35 + margin 0.15 = 0.60` 이었다.
L2에서 `min_range` 가 0.05가 되면서 **사각의 실효 경계가 센서에서 ROI 크롭으로 이동**한다.
즉 상수가 아니라 **유도식의 입력 심볼이 교체**된 경우다.

```
v2:  boundary = min_range(0.8)
v3:  boundary = max(min_range 0.05, self_x_max 0.45, roi_x_min 0.5) = 0.5
     clearance 기준 = 0.5 − 0.35 + 0.15 = 0.30
```

| 파라미터 | v2 | v3 | status |
|---|---|---|---|
| `emergency_clearance` | 0.60 | **0.30** | INVALID → PROVISIONAL |
| `blind_hold_clearance` | 0.60 | **0.30** | INVALID → PROVISIONAL |

원칙(정지 결정 경계는 사각 밖) 은 불변이고, 구조적 동형도 유지된다:
v2 `0.60+0.35=0.95 ≥ 0.8+0.15` ↔ v3 `0.30+0.35=0.65 ≥ 0.5+0.15`.

> ⚠ 완화 방향 변경이므로 **head_on·static_stop N≥5 재통과로만 유효화**된다
> (대장 note에 조건 명기). 실기 `min_range` 0.05 확정 시 blind-hold 메커니즘
> 존속 자체를 재평가한다.

### 2.2 프레임 주기(T_frame) 의존

| 파라미터 | v2 (T_frame 0.10) | v3 (T_frame 0.18) | 유도 |
|---|---|---|---|
| `publish_rate` | 10.0 | **5.55** | `= f_scan` |
| `assoc_max_dist` | 1.6 | **2.2** | `v_max 7.0 × T_frame + 여유 0.9` (프레임당 변위 0.75 → 1.26 m) |
| `vel_max_dt` | 0.5 | **0.8** | `(track_coast_frames 3 + 1) × 0.18 = 0.72` + 여유 |
| `sensor_timeout` | 0.5 | **0.9** | `5 × T_frame` (구판은 L2에서 3프레임 미만 → 오탐 STOP) |
| `cvm_latency_max` | 0.3 | **0.5** | `T_frame 0.18 + 열화 0.10 + 처리` — 구판은 실측 지연을 클립 |
| `track_coast_frames` | 3 | 3 (유지) | 프레임 단위이므로 코스팅 0.30 → **0.54 s** 로 실효 변화 |
| `fast_trig_frames` | 4 | 4 (유지) | 확정 지연 0.40 → **0.72 s** (§1.4 표 첫 행과 일치) |

`vel_max_dt` 는 v2에 잠재한 정합 결함이기도 했다: 코스팅 상한 직후 재연관 시
`dtm = 4 × T_frame = 0.72 s` 가 상한 0.5를 넘어 **속도 갱신이 조용히 스킵**되고
스테일 속도가 유지된다. L2에서 이 구간이 실사용 대역으로 들어와 명시 수정했다.

### 2.3 self-filter (시뮬 판, §6.1)

| 파라미터 | v2 | v3 | 유도 |
|---|---|---|---|
| `self_x_min/max` | ∓0.40 | **∓0.45** | `robot_half_length 0.35 + 다리 전후 스윙·마운트 0.10` |
| `self_y_*`, `self_z_*` | 유지 | 유지 | 측·수직은 시뮬에서 자기 유입 미관측 |

전제 자체가 바뀌었다. v2 헤더는 *"L1 min range 0.8이 몸체 대부분을 제거하므로
이 박스는 안전망"* 이었다 — L2(0.05 m)에서는 **박스가 1차 방어선**이 된다.
시뮬 G0는 `empty` 시나리오(보행 중 자기 유래 클러스터 0)로 판정한다.
실기체 판(gait 의존 다리 스윙 영역)은 P8'에서 측정 9D로 재조정한다.

### 2.4 열화 프로파일 (§6.5)

| 프로파일 | keep | dropout | noise | latency | status |
|---|---|---|---|---|---|
| `real_l1` | 0.20 | 0.10 | 0.03 | 0.10 | **DEPRECATED** (v2 재현 전용) |
| `worst_case` | 0.10 | 0.20 | 0.05 | 0.20 | **DEPRECATED** |
| **`real_l2`** | **1.0** | 0.10 | 0.02 | 0.10 | PROVISIONAL |
| **`worst_case_l2`** | 0.50 | 0.20 | 0.05 | 0.20 | PROVISIONAL |

`real_l2` 의 `density_keep_ratio` 가 1.0인 것이 핵심 델타다. `real_l1` 의 0.20은
*시뮬 균일 링(180,000 pts/s)을 L1 유효율로 깎는* 계수였다. 시뮬 센서가 이미
L2 공칭 포인트율로 내려온 지금 같은 계수를 얹으면 **이중 열화**가 된다.
따라서 `real_l2` 는 gz 라이다가 표현하지 못하는 것(비반복 스캔 커버리지 요동,
저반사 dropout, 측정 정확도, 파이프라인 지연)만 담당한다.

> ⚠ `real_l1` 은 반드시 `lidar_gen:=l1` 과 함께 써야 한다 (프로파일 헤더에 명기).

## 3. 🔴 재기준화 중 발견된 하네스 결함 3건

### 3.1 회귀 하네스가 시행 간 프로세스를 정리하지 못함

`kill_gazebo_leftovers()` 가 `gz sim` 과 `parameter_bridge` 만 종료하고
launch 가 띄우는 나머지 노드를 남겼다. launch 가 SIGINT 에 완전히 죽지 않으면
이들이 살아남아 다음 시행과 같은 ROS 그래프에 계속 발행한다.
**두 가지 형태로 나타났고, 둘 다 실측했다.**

**(a) 지각·게이트 노드 생존** — 이전 시뮬의 장애물로 STOP/STUCK 난사.
유령 노드 **34분 생존** 실측. 이 상태의 판정은 전부 무의미했다.

```
오염:   static_stop  travel 0.00m  STUCK/NOMINAL 수백 회 → ESTOP
        (변경 전 코드 대조군도 동일: travel 1.70m, STOP 진입 145회
         — 즉 v2 baseline 자체가 재현되지 않았다)
정리 후: static_stop  travel 10.20m  SLOW_DOWN/NOMINAL  PASS
```

**(b) TF/odom 발행 노드 생존** — 더 나쁘다. `ekf_node`,
`state_estimation_node`, `robot_state_publisher`, `static_transform_publisher`
가 살아남으면 다음 시행의 TF 트리가 오염돼 **`/obstacles/lidar` 가 영영 나오지
않는다**. 한 번 발생하면 이후 모든 시행이 연쇄로 죽는다.

```
1차 스윕: bike_pass ×5 + crossing ×5 = 10연속 readiness timeout
정리 후:  crossing 단독 실행 PASS (min_clr 0.651)
```

→ `LEFTOVER_PATTERNS` 를 launch 의 `executable=` 전수와 일치시켰다
(`verification/run_scenario.py`). 드라이버(`cmd_publisher`)는 실행 중 자기
자신을 죽이므로 제외하고, `create`/`spawner` 같은 흔한 이름은 경로째로
매칭해 무관한 프로세스를 죽이지 않는다.
목록이 다시 썩지 않도록 **`test_harness_cleanup.py`** 가 launch 노드 누락을
차단한다 — launch 에 노드를 추가하면 이 테스트가 먼저 깨진다.

> 이 결함은 L2와 무관하며 **v2 baseline 수치의 신뢰도에도 소급 적용**된다.
> 과거 회귀에 산발적으로 나타난 설명되지 않는 STUCK/STOP 이상치와
> `phase5_metrics.csv` 의 static_stop FAIL 2건의 유력한 후보다.

### 3.1b 하네스 시간 상한이 옛 운영점에 묶여 있었다

RTF 캡(§3.2)으로 시행의 벽시계 소요가 ~2.5배가 되면서 두 상한이 부족해졌다.

| 상한 | 구판 | 신판 | 사유 |
|---|---|---|---|
| 드라이버 readiness | 180 s | **300 s** | 준비까지 필요한 sim time 이 그대로 4배 벽시계 (RTF 0.25) |
| 하네스 `wall_cap` | `60 + 4·(settle+duration)` | **`330 + 8·(…)`** | 구판 상수 60이 드라이버 자신의 readiness 상한보다 작아 **하네스가 드라이버보다 먼저 끊었다** |

배수를 4 → 8로 올린 근거: **RTF 0.25는 캡이지 하한이 아니다.** 웨지되거나
경합이 심하면 실효 RTF 가 그 아래로 떨어진다 — 실제로 `bike_pass` 한 시행이
33 s 시뮬에 462 s 를 넘겨 잘렸다. 여유는 웨지된 시행에서만 비용이 되므로
넉넉히 잡는다.

> ⚠ 정정: 이 근거를 처음 쓸 때 위 시행을 "실측 RTF 0.07" 로 서술했으나
> 정확하지 않다. 정상 완료한 96 시행의 실효 RTF 는 **최소 0.243 · 중앙 0.248**
> 로 캡에 붙어 있었다(로그 복원). 462 s 시행은 매끄럽게 느려진 것이 아니라
> **멈춘(wedge) 것**이며, 그런 시행은 어떤 상한으로도 구제되지 않는다 —
> 상한을 늘린 실익은 "기동이 느린 정상 시행을 인프라 실패로 오기록하지 않는 것"에 있다.

### 3.2 base 월드에 RTF 캡이 없다 — 운영점이 머신 부하에 좌우된다

회귀 하네스의 base 월드(`small_city.sdf`)에는 RTF 캡이 없다. 캡이 명시된 것은
`small_city_test*.sdf`(별도 경로)뿐이었다. 즉 회귀의 운영점이 **머신 부하에
따라 달라진다**.

맞춰야 하는 것은 RTF 가 아니라 **심시간 라이다 주기 0.18 s** 다. 관계는

```
심시간 라이다 주파수 = C / RTF        (C = GPU 벽시계 라이다 렌더율)
5.55 Hz 를 얻으려면   RTF ≤ C / 5.55
```

### 측정 1 — 라이다는 캡을 요구하지 않는다

(2026-08-05, 클린, `bike_pass` 월드 = GLB 자전거 메시 + actor, 최대 부하)

| 설정 RTF | 실효 RTF | 심시간 주기 median/**p90** | 심시간 주파수 |
|---|---|---|---|
| 0.25 | 0.249 | 0.180 / **0.180** | 5.56 Hz |
| 0.45 | 0.442 | 0.180 / **0.180** | 5.56 Hz |
| 0.60 | 0.560 | 0.180 / **0.180** | 5.56 Hz |
| 1.0 (무제한) | 0.672 | 0.180 / **0.180** | 5.56 Hz |

**어느 지점에서도 주기가 열화되지 않는다.** gz 는 렌더가 밀리면 프레임을 버리는
게 아니라 **시뮬 전체를 늦춰** 센서 스케줄을 지킨다 — 그래서 한계가 "주기 열화"가
아니라 **"RTF 포화"**(이 머신 0.672)로 나타난다. 초기 모델
(`심시간 주파수 = C / RTF` 로 프레임이 드롭된다)은 이 점에서 틀렸다.

### 측정 2 — 🔴 캡을 결정하는 것은 보행 제어 충실도다

`CHAMP quadruped_controller` 는 joint 명령을 **벽시계 고정 ~200 Hz** 로 낸다
(심 시간 기준이 아니다). 따라서 심시간 실효 제어율이 RTF 에 반비례한다:

| 설정 RTF | CHAMP 벽시계 | **CHAMP 심시간** | 게이트 루프 심시간 |
|---|---|---|---|
| 0.25 | 200.3 Hz | **809 Hz** | 50.2 Hz (설정 50) |
| 0.45 | 201.3 Hz | **462 Hz** | 50.7 Hz (설정 50) |

게이트 루프는 두 지점 모두 멀쩡하다 — 바뀌는 것은 지각·판단이 아니라
**로코모션**이다. RTF 를 올리면 로봇이 1 심시간초당 받는 보행 제어 갱신이
거의 절반으로 줄어든다.

**0.45 등가성 검증 (N=5, 0.25 baseline 대비) — 실패:**

| 시나리오 | RTF 0.45 | RTF 0.25 baseline | 비고 |
|---|---|---|---|
| `head_on` | **3/5** | 5/5 | baseline 에 없던 실패 유형 — `robot_y` 밴드 이탈 6.35/6.36. 양보 기동이 오버슈트해 연석을 넘는다 |
| `social_yield` | **2/5** | 8/10 | |
| `bike_head_on_4ms` | 5/5 | 5/5 | 유지 — fast-class 는 판단 지배적이라 둔감 |

→ **0.25 유지.** 회귀 96 시행의 실효 RTF 는 최소 0.243 · p10 0.247 · 중앙 0.248
(캡 미달 1/96)로 **머신이 아니라 캡이 구속**이었지만, 그 구속이 P4/P5 튜닝의
전제였다. 캡을 바꾸려면 전 시나리오 재기준화가 필요하다.

**비용**: 0.25 는 포화 RTF 0.672 대비 시행 벽시계가 ~2.7배다(전 회귀 ~3시간).
이 비용은 "더 빠른 캡"으로 줄일 수 없다 — 위가 그 이유다.

> ⚠ **정정 (2026-08-05).** 이 절의 이전 판은 "캡 없으면 심시간 1.4 Hz 로 붕괴 /
> RTF 캡은 게이트 성립 조건"이라 단정했다. **근거가 된 두 측정이 모두 오염돼
> 있었다** — 정리 목록에 `ekf_node`·`state_estimation_node` 가 빠져 유령 노드가
> 살아 있었고(§3.1), 붕괴 수치는 로드 17~36 구간에서 측정됐다. 완전 정리 후
> A/B(`static_stop` N=3): 캡 O 0/3(0.292~0.353) · 캡 X 0/3(0.302~0.343) —
> 구분 불가. **캡은 게이트 성립 조건이 아니다.** 뒤이어 0.45 로 완화를
> 시도했다가 위 측정 2로 기각했다 — 캡의 진짜 근거는 센서가 아니라
> 로코모션이라는 것이 최종 결론이다.

→ `verification/worlds.py::generate_world` 가 월드 생성 시 캡(`RTF_CAP = 0.25`)을
주입한다. `P35_RTF_CAP` 로 값을 덮거나 `0` 으로 끌 수 있다(대조 실험용).

**이것이 §6.6 v3.1 항목 "RTF 운영점 재유도"의 답이다**: 운영점을 고정하되,
그 근거는 센서가 아니라 **보행 제어 충실도**다. 시뮬 RTF 는 "얼마나 빨리 도는가"가
아니라 **"로봇이 1 심시간초당 몇 번 제어되는가"** 를 정하는 값이며,
P4/P5 튜닝 전체가 이 운영점 위에 서 있다.

> 📌 sim2real 함의: 실기에는 RTF 가 없고 CHAMP 도 실시간 200 Hz 로 돈다.
> 즉 **시뮬 RTF 0.25 는 실기보다 4배 조밀한 보행 제어**(심시간 809 Hz)를
> 준다는 뜻이다. 시뮬이 로코모션 측면에서 실기보다 낙관적일 수 있다 —
> P8' 실기 측정 9(스텝 응답)에서 이 격차를 확인해야 한다.

### 5.2 🔴 `static_stop` — 거동 자체가 바뀌었다 (기준 재검토 필요)

**충돌·이격 문제가 아니다.** 8회(클린 5 + 열화 3) 전부 접촉 0, 이격
0.319~0.384 로 v2 의 우회 경로(0.124~0.284)보다 **안전하다**.
실패 사유는 단 하나 — `require_states: [SLOW_DOWN]` 미충족이다.

```
관측 거동 (static_stop #3, oracle):
  robot_x 15.00 → 5.97   (보행자 x=10 통과)
  robot_y 5.20 → 4.18    횡방향 우회 1.03 m
  states  (없음)          NOMINAL 유지 — 감속 상태 미진입
```

즉 로봇이 **감속·정지 대신 소셜 레이어의 우회로 처리**한다.

이것은 L2 가 새로 만든 문제가 아니다. `phase5_metrics.csv` 에 **이미 같은
신호가 있다**:

| v2 phase5 static_stop | travel | 이격 | states |
|---|---|---|---|
| PASS | 4.899 | 0.983 | 정지 경로 |
| FAIL | 10.718 | 0.124 | 우회 경로 |
| **FAIL** | **10.330** | **0.203** | **(없음) ← L2 와 동일 신호** |
| PASS | 4.748 | 0.698 | 정지 경로 |
| PASS | 10.270 | 0.284 | 우회 경로 |

v2 는 "정지 경로 / 우회 경로"가 섞이는 **양봉 상태**였고, L2 는 이를
우회 경로로 **일관되게 수렴**시켰다(열화 3/3 동일 → 흔들림이 아니라 결정적).

> **판정 기준은 소셜 레이어 이전(v2)의 "감속 후 정지" 기대를 인코딩하고 있다.**
> 같은 상황에서 `head_on.yaml` 은 이미 기준을 YIELD 경로로 갱신한 전례가 있다
> (파일 헤더: "v2까지는 코리도 TTC 경로를 게이트했으나, 소셜 ON에서는 …
> 판정을 YIELD 경로로 갱신"). `static_stop` 에 같은 처리를 할지는
> **거동 의도에 대한 결정**이므로 이 문서에서 임의로 바꾸지 않고 남긴다.
> 결정 시 확인할 것: 우회 통과 시 이격 0.32~0.38 m 가 사람 인접 통과 정책
> (`pass_speed_cap` 0.3 m/s, `person_margin` 0.45)과 정합하는가.

### 5.3 🔴 `social_yield` — 양보 래치 타이밍 산포가 넓어졌다 (재현됨)

N=5 로는 단발 이상치와 구분되지 않아 **N=10 까지 늘려 확인했다**.

| | 최소 이격 |
|---|---|
| v2 (N=5) | 0.180 · 0.215 · 0.215 · 0.215 · 0.230 — 폭 **0.050**, 5/5 PASS |
| L2 (N=10) | **0.045** · **0.048** · 0.109 · 0.196 · 0.207 · 0.229 · 0.234 · 0.239 · 0.242 · 0.248 — 폭 **0.203**, **8/10** PASS |

중앙값은 유지된다(v2 0.215 vs L2 0.218). **바뀐 것은 하단 꼬리**다 —
두 블록 각각에서 재현됐으므로 단발 이상치가 아니다.
**접촉은 10회 전부 0** — 시나리오가 하드 라인으로 규정한 조건은 유지됐다.

시나리오 주석이 이미 "래치 타이밍 런 편차로 walker 여유 0.10~0.69 산포"를
기록하고 있다. L2 의 프레임 주기가 0.10 → 0.18 s 로 늘어 **래치 시점의 양자화가
거칠어진 것**이 산포 확대의 유력한 기전이다. 같은 시나리오 주석이 여유 상향을
"래치 안정화 튜닝 항목"으로 분류하고 있으므로 **재기준화 범위 밖**이며,
Phase 5'(C3 이관) 에서 다룬다.

> 이것은 sim2real 예측에 직접 관련되는 종류의 델타다. 실기 L2 도 5.55 Hz 이므로
> **동일한 하단 꼬리가 실기에서도 나타날 것**으로 예측한다 — P9 실기 검증에서
> 이 예측의 적중 여부가 열화 하네스 유효성의 직접 증거가 된다.
